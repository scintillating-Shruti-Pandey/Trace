# TRACE — Teacher Presentation Guide

**Purpose:** Help the team explain the project clearly, demonstrate the parts that are real and working, and answer technical questions without overstating results.

**Project:** TRACE — Multimodal Manufacturing Intelligence & Video Search
**Report date:** 26 November 2026 (Asia/Calcutta)
**Evidence basis:** Repository implementation, `records/ENGINEERING_SPEC.md`, `docs/build-status.md`, and the recorded evaluation report at `docs/eval-reports/final.md`.

> **The safest presentation framing:** TRACE is a manufacturing evidence search and visual-analysis prototype. It can retrieve manufacturing video moments and connect them to images and technical documents. Its Visual Studio Lab page processes real IndEgo frames and short real-video intervals with classical OpenCV methods. It does not detect defects, generate the existing captions, or transcribe the current video corpus.

## 1. The 30-second explanation

> “TRACE helps a user find a useful moment in manufacturing video and connect that moment to related technical evidence, such as a manual passage or inspection document. We built a web application and a linked corpus of real IndEgo videos, annotated segments, keyframes, technical documents, and human-authored evidence links. The Visual Studio Lab lets us inspect a real frame and demonstrate image-processing techniques, keyframe selection, and motion analysis on a short video interval. We evaluated retrieval and grounded answers separately. Some targets were met, and some remain open; I’ll distinguish those rather than present development results as held-out results.”

## 2. What problem TRACE addresses

Manufacturing knowledge is spread across different kinds of evidence. A video may show an operation, a maintenance report may record an observed problem, and a manual may state a relevant specification. Searching each source separately makes it difficult to move from a natural-language question to the exact time in a video and then to supporting documents.

TRACE is designed to connect those pieces. For a query such as “find the lower-hinge assembly step and its specified tightening torque,” the intended workflow is:

1. Find relevant videos or video segments.
2. Refine the result to a timestamped moment.
3. Retrieve relevant manual or report passages and, when useful, keyframes.
4. Present the evidence together so a person can verify the answer.

The distinguishing idea is the **evidence connection between modalities**: video moments, still images, documents, and explicit links between evidence items. It is a retrieval and inspection prototype, not an automated maintenance authority.

The video source is Fraunhofer IPK’s IndEgo dataset, pinned in the application manifest to revision `c822468b5e0c9c42ebbf2939d3be936c2b203704`. The manifest records a CC BY 4.0 license. The stored catalogue count is not a claim that every video was reprocessed during the Visual Studio Lab demo.

### Important caption distinction

The current video text is **not generated by a vision-language model**. The indexed segment text comes from IndEgo human keystep annotations and text constructed from available metadata/annotations for fixed windows. “Vectorizing captions” means converting that existing text to numeric embeddings for search. It does not mean TRACE generated those captions.

Likewise, the current corpus does not contain pipeline-generated Whisper transcripts or word-level speech timestamps. Do not describe the human keystep text as speech transcription.

## 4. How the system is built

### Main services

- **FastAPI** exposes the application pages and JSON/SSE endpoints.
- **PostgreSQL with pgvector** stores corpus metadata, evidence relations, and dense-vector indices. PostgreSQL full-text search with a GIN index supplies the lexical document lane.
- **Redis** supports the service stack and job infrastructure.
- **BGE-M3** is the text embedding model used historically for video-segment/window text and document chunks (1,024 dimensions).
- **SigLIP 2** is used historically for keyframe/image representations (1,152 dimensions) and visual-text fusion.
- **Ollama** is the local-model interface used/configured for grounded generation and optional local helpers. Availability at a particular presentation requires a fresh runtime check.
- **The browser pages** include the search/seek demo, corpus explorer, evaluation dashboard, and the Visual Studio Lab.

### Retrieval and answer flow

1. **Text query:** The query is embedded for dense search. Document retrieval also uses lexical full-text ranking.
2. **Rank fusion:** Dense and lexical document results are combined with Reciprocal Rank Fusion (RRF), which combines ranks instead of comparing scores on different scales.
3. **Video and image evidence:** Video text and visual keyframe lanes provide candidate evidence. The implementation also expands candidates through recorded evidence links. Image search is available separately; the search path does not globally fuse four video/document/image lanes into one universal RRF list.
4. **Temporal refinement:** A coarse segment can be narrowed with a sliding time window and lexical overlap between query terms and annotated caption/action text. This is heuristic refinement, not visual action recognition. ASR word times are accepted by an optional adapter but are not currently present in corpus data.
5. **Evidence assembly:** Video moments, document chunks, and images receive evidence identifiers such as `[E1]`.
6. **Grounded response:** The generator is designed to answer from the supplied evidence, cite evidence IDs, and abstain when evidence is insufficient. API validation checks that citation IDs belong to the retrieved set. That check prevents unsupported IDs but does not, by itself, prove that every cited statement is semantically supported.
7. **Verification in the UI:** A user can follow a video citation to a timestamp or inspect a related document/keyframe.

### Human-authored evidence links

The 154 stored evidence links are explicit relations, not automatic model discoveries:

| Relation | Count | Plain-language meaning |
|---|---:|---|
| `documents` | 85 | Evidence items are associated through the document relation |
| `specifies` | 41 | A document/evidence item specifies a requirement or detail |
| `depicts` | 16 | An evidence item depicts a related item or event |
| `contradicts` | 12 | Linked evidence items disagree |

These links support multi-hop retrieval and allow conflicting evidence to be surfaced. Their quality depends on the human curation process.

## 5. The Image and Video Processing studio

The standalone page is available at `/ivp` when the local API is running. Unlike the earlier CAD reconstruction, this page is backed by real IndEgo source-video reads.

### Real-video path

1. The page loads the video catalogue and the presenter selects a video and timestamp.
2. The browser asks TRACE’s media proxy for the remote source media.
3. The backend uses FFmpeg to decode a bounded set of frames into memory.
4. OpenCV and NumPy produce the requested image/video analyses.
5. The response returns visual outputs and metrics to the page. The IVP frame path sends `Cache-Control: no-store`; decoded media is handled in bounded memory, not saved as a local video corpus.

The interval analyzer caps a request at 90 seconds and 24 sampled frames, and clamps sampling between 0.25 and 4 frames per second. This makes the operation bounded; it is not a live-camera pipeline.

### Techniques implemented

| Technique | What to say in plain language |
|---|---|
| Color-space conversion | Shows the same frame as RGB, grayscale, HSV, and LAB so color and brightness can be considered separately. |
| Histograms and CLAHE | Summarizes pixel-intensity distributions and applies local contrast enhancement. |
| Filtering | Demonstrates Gaussian smoothing, sharpening, embossing, and Laplacian response. |
| Edge detection | Shows Sobel gradients and Canny edge maps to reveal intensity boundaries. |
| Morphology | Applies thresholding and operations such as erosion, dilation, opening, and closing to binary structures. |
| SIFT and ORB | Marks local keypoints/features that can help compare visual structure. |
| HOG | Displays a gradient-orientation descriptor used to summarize local shape/edge patterns. |
| Keyframe selection | Compares adjacent grayscale frames and selects frames whose mean change exceeds a threshold, subject to a minimum time gap. It also reports edge density and Laplacian-variance sharpness. |
| Optical flow | Estimates apparent pixel motion between consecutive frames with sparse Lucas–Kanade and dense Farneback methods. |

**Important optical-flow detail:** The single-frame processing function can create a small translated companion frame for an illustrative optical-flow result. The Visual Studio Lab page omits that synthetic flow in its single-frame UI. When explaining real video motion, use the segment analysis output, which calculates flow from consecutive source-video frames.

## 7. Evaluation: what the numbers actually mean

The following are **historical evaluation results**, not new runs for this presentation. The main held-out scorecard reports 2 of 6 Definition-of-Done targets met, one below target, and three without sufficient held-out evidence.

| Acceptance criterion | Target | Recorded result | Correct interpretation |
|---|---:|---:|---|
| Video segment Recall@5 | ≥70% | **63.3% (19/30)** on locked test | Below target. Development result was 88.5%, which must not replace the test figure. |
| Document chunk Recall@5 | ≥80% | **100.0%** across 15 document queries over 3 runs | Target met on the recorded held-out evaluation. |
| Grounded answer faithfulness | ≥85% | **90.4%** on 30 multi-hop test items over 3 runs | Target met under the recorded judge protocol; human spot-check agreement is reported separately. |
| Temporal IoU | Mean ≥0.40 | **0.7477 on development (n=26)**; locked-test result not reported | Not established for held-out acceptance. |
| Lift over text-only | Positive on held-out | **+46.7 percentage points on development (n=30)**; no held-out comparison reported | Development-only evidence. Do not call it a test-set improvement. |
| Full-loop UI latency | p95 <5 seconds | **p95 not reported**; recorded three-run mean was 381.1 ms | Criterion not established. Mean is not p95. |

Other useful results, with their split and task kept explicit:

- Whole-video retrieval Recall@5 was recorded as **96.2%** (Phase 1 result).
- Keyframe visual retrieval Recall@5 was **90.0% on the visual development set (n=20)**. The final report’s locked-test table records **40.0% visual Recall@5**, so generalization is a limitation.
- Document hybrid retrieval recorded 100% Recall@5 and MRR@20 of 0.9333 on its development evaluation.
- Temporal localization recorded Mean IoU 0.7477 on development only.
- The grounded-answer evaluation recorded 10/10 abstentions on its unanswerable sample. Abstention is an additional result, not one of the six acceptance criteria.
- Human spot-check of the judge reported 93.3% agreement (28/30 atomic verdicts) and Cohen’s κ = 0.8667.

### Ablation caveats you should know

The runner contains 11 labels, A0–A10, but not every label implements the intended spec component:

- A6 is a fixed 1.1 score multiplier on linked segments, not a learned cross-encoder or genuine reranker.
- A7 does not include the full specified query-analysis and LLM-reranker path.
- A8 runs the same implementation as A7, so A7/A8 cannot measure the contribution of query analysis.
- A5/A4 is not a significant top-5 improvement: the paired top-5 change was −3.3 percentage points, with p=0.3598. Some top-10 and MRR differences are descriptive because their paired tests were not computed.
- Raw per-query ablation values were not archived for an independent recomputation in the later compliance audit.

Say: “We ran and documented an ablation matrix, and the compliance audit identified where some configuration labels overstate what the code actually ablates. We report that limitation rather than claiming every intended ablation was valid.”

## 8. Cost, privacy, and deployment boundaries

- Evaluation and model use described in the historical reports were local, with **$0 paid API spend**. No hosted AI service is part of the approved plan.
- Remote IndEgo video is read on demand; the IVP path processes bounded data in memory and does not create a local media archive.
- Current AI caption/ASR outputs are not persisted. Database persistence, re-embedding, and full-corpus indexing of generated outputs have not been approved or implemented.
- PostgreSQL, Redis, and the API have previously been verified healthy. In a later runtime audit, the API could not reach the BGE and SigLIP microservice ports (8001/8002). Verify live service state before promising a working search demo.
- Historical evaluation metadata records an RTX 4050 Laptop GPU. The current user-provided Windows Task Manager screenshots show Intel Iris Xe integrated graphics with shared memory, while the WSL Docker environment could not expose a GPU adapter. Treat this as a hardware/runtime discrepancy; do not attribute the historical benchmark to the current presentation machine without confirmation.
- The running API container's OpenCV 5.1.0 reports OpenCL unavailable (`haveOpenCL=False`, `useOpenCL=False`), so its classical IVP operations currently run on CPU rather than the host Intel GPU.
- The latest screenshot showed 2.2 GB RAM available (13.4/15.6 GB in use). Do not load the large AI models during presentation preparation. The presentational IVP workflow does not require those models.

## 9. Suggested presentation flow (about 5 minutes)

### 0:00–0:40 — State the problem

“A manufacturing procedure can be visible in a video, described in a manual, and recorded in an inspection report. TRACE brings those evidence types into one search-and-inspection workflow and keeps the video timestamp available for verification.”

### 0:40–1:20 — Explain the data

“We curated a bounded corpus of 25 real IndEgo videos and linked it to technical documents and human-annotated segments. We also have keyframes and 154 curated evidence links. The existing captions are human keystep annotations; they were not generated by an AI captioning model.”

### 1:20–3:40 — Demonstrate `/ivp`

1. Open `/ivp` and choose a real IndEgo video.
2. Select a timestamp and point out that the displayed frame comes from the source video, not a CAD reconstruction.
3. Run the single-frame analysis and explain one or two outputs: for example, Canny edges and LAB/CLAHE contrast.
4. Select a short interval and show chosen keyframes/timestamps.
5. Show optical-flow output from that real interval. Explain that it estimates apparent pixel motion between adjacent source frames; it does not label an action.
6. Give the recorded example only as a diagnostic: one eight-second window sampled 16 frames and selected three keyframes. Do not imply this count applies to every video.

### 3:40–4:30 — Connect IVP to TRACE

“The Visual Studio Lab is one part of a broader evidence-search system. BGE-M3 historically indexes the text side, SigLIP 2 the image side, and PostgreSQL stores vectors and evidence relations. Dense and lexical document results are combined with RRF. The video player and citations let a user inspect retrieved moments and sources.”

Only demonstrate `/`, `/corpus`, or `/eval` if the API and required model endpoints are healthy at that moment. The BGE/SigLIP endpoints were unavailable in the last recorded runtime audit.

### 4:30–5:00 — Close with evidence and limitations

“We measured retrieval, temporal localization, and answer faithfulness separately. On the locked test, document Recall@5 and answer faithfulness met their targets, while video segment Recall@5 was 63.3% against a 70% target. Some other targets remain unreported on held-out data. Our next step is to strengthen generalization and validate the complete UI path; generated captioning and speech transcription are not claimed as completed.”

## 10. Likely teacher questions

### “Is this actually processing the dataset video, or is it still CAD?”

“The `/ivp` frame and interval endpoints now read the pinned real IndEgo source through the media proxy. The recorded live check decoded a real frame and analyzed a real eight-second interval. The earlier CAD reconstruction is not the source for this IVP page.”

### “Are the captions produced by AI?”

“No. Existing indexed video text comes from IndEgo human annotations and metadata-derived windows. We prepared optional code for local VLM captioning, but no vision model was downloaded or run, so we do not call those machine captions.”

### “Do you have speech transcripts?”

“Not in the current indexed corpus. We installed the optional faster-whisper package in the host project environment, but did not download the large-v3 weights or run transcription. The API route is disabled by default.”

### “What does vectorization mean here?”

“An embedding model maps text or an image to a numeric vector so related items can be ranked by similarity. BGE-M3 is the historical text encoder; SigLIP 2 is the image encoder. This is different from generating a natural-language caption.”

### “Does TRACE detect defects or certify safety?”

“No. It retrieves and displays evidence and computes generic image/video features. It is not a trained defect classifier, safety system, or production inspection authority.”

### “How do you find the timestamp?”

“The retrieval system starts from annotated video segments/windows. A lexical sliding-window heuristic can narrow a coarse interval, and the UI seeks to the returned time with a short lead-in. This is not a learned visual action-localization model. The strong Mean IoU result currently reported is development-only; a locked-test IoU result is not reported.”

### “Why use both dense and lexical retrieval?”

“Dense search can match related meaning even when wording differs. Lexical search can preserve exact terms such as part names and specifications. RRF combines the ranks without treating their raw scores as directly comparable.”

### “What is novel about the project?”

“The project’s contribution is the linked workflow: timestamped manufacturing video evidence, keyframe search, technical-document retrieval, human-authored cross-modal links, and citation-based inspection. We do not claim a new foundation model or model training.”

### “Did all targets pass?”

“No. The final audit reports 2 of 6 held-out Definition-of-Done targets met. Document Recall@5 and faithfulness met their targets; video segment Recall@5 was below target; held-out temporal IoU, held-out lift, and full-loop UI p95 were not established.”

### “Why not run AI captions now that you have a GPU?”

“The current screenshot shows Intel integrated graphics using shared system memory, and the machine still has high RAM use. The WSL container does not expose a GPU adapter. We have not verified that the chosen local model stack can use this GPU safely. The AI path is optional; the real-video classical IVP demo works without it.”

### “Can the system ingest a new video live?”

“Not through the current default configuration. MinIO and the background ingestion worker are deferred; the live camera path is out of scope. The IVP demo reads selected remote dataset videos on demand.”

## 11. What not to claim

Avoid these statements:

- “The system generates captions for all videos.”
- “Whisper transcripts and word timestamps are indexed in the corpus.”
- “The project detects defects or automatically makes maintenance decisions.”
- “All six acceptance targets passed.”
- “The +46.7-point gain is a held-out test result.” It is a development comparison.
- “Temporal IoU is 0.7477 on the test set.” It is a development result; locked-test IoU is not reported.
- “The 381.1 ms value is p95.” It is a three-run mean; p95 was not reported for the full loop.
- “Every A0–A10 configuration implements the intended spec component.” The audit found important ablation mismatches.
- “The current presentation laptop is the RTX 4050 machine used in the historical evaluation.” Current screenshots show Intel Iris Xe and the runtime discrepancy has not been resolved.
- “The browser UI was fully end-to-end tested in the latest IVP live check.” The HTTP routes were checked; browser rendering/button interaction was not separately exercised in that check.
